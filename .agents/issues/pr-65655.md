## 正文

## Summary

`ChatCompletionEventMapper::map_event` only emits a streamed tool call once it
has both a non-empty id and a name, but the `finish_reason == "tool_calls"`
drain pushed every accumulated call unconditionally. A call whose id never
arrived was still emitted with an empty `tool_call_id`, stored in the thread,
and rejected by the provider on the next request; retrying resent the same
history and left the thread stuck.

This mirrors the per-delta guard on the drain: well-formed siblings are still
emitted, and if any call lacks an id or a name the response fails with a new
`InvalidProviderOutput` error instead of ending the turn as a successful tool
call. The error is not transient, so the agent does not retry it automatically.

I deliberately did not synthesize an id. That would store data the provider
never issued, and deriving it from the stream `index` is not reliable because
providers reuse indices (`separates_parallel_tool_calls_sharing_an_index`).
If you would rather keep the turn going, a `{name}-{position}`-style id would
be unique within the response and easy to trace.

Note that this makes the mapper's contract slightly weaker: a `tool_calls`
finish can now produce no `Stop` event, which is documented on
`ChatCompletionEventMapper` for the providers that share it. The diagnostic also
logs only a bounded preview of the arguments (200 chars) instead of the full
payload, which can be large and often contains local paths.

Closes #65655.

Related: #65859 takes the synthesize-an-id approach for the same issue.

## Testing

`cargo test -p language_model_core --lib` (74 pass), plus
`cargo clippy -p language_model_core --all-targets -- -D warnings` and
`cargo fmt -p language_model_core -- --check`.

New tests drive the mapper directly with a finish chunk and cover:

- an empty or absent id, an empty or absent name, and both missing (six shapes);
- the malformed call is never emitted as a tool use, and no `ToolUse` stop is
  reported;
- a well-formed sibling is emitted, in order, before the error.

I could not reproduce this on demand with a live provider, so the regression
tests construct the chunks explicitly.
